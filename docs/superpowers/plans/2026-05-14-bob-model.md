**Goal:** Add `/bob-model` — a domain-modeling skill that consumes a PM-style requirement doc (md/pdf/docx/txt) and produces a 5-section domain model snapshot in both machine-readable markdown (SSoT) and a self-contained HTML view (Mermaid via CDN). Slots between `/bob-survey` and `/bob-stories`.

The only other run-bob template change is appending a soft prompt to `bob-survey.md`'s "下一步" section pointing at `/bob-model`.

**Tech Stack:** Rust 1.75+, clap 4.5.4, anyhow 1.0, colored 2.1, dev-dep tempfile 3. **No new crates.**

## Architectural Notes for the Engineer

Read these before starting — they explain decisions not obvious from individual tasks.

### 1. The spec says to update CLAUDE.md's workflow graph — don't

The spec's §4 says "需要在工作流总览图里加一行 `/bob-model`". When the plan was being written, the actual `## 工作流总览` graph in `src/templates/root/CLAUDE.md` (lines 284–310 area) was inspected and found to contain **only the 3 core skills** (`/bob-identify` → `/bob-onion` → `/bob-spec`). The newer skills `/bob-survey`, `/bob-stories`, `/bob-nfr`, `/bob-compliance` are NOT in the graph either. Adding `/bob-model` would be inconsistent with how those 4 are handled (none of them have a graph row).

**Decision:** skip the CLAUDE.md graph change. Model is discoverable via:
- `bob-survey.md`'s 下一步 soft prompt (Task 5)
- The skill itself living in `.claude/skills/bob-model/`
- The README rewrite that's already on master (mentions `/bob-model`... actually NO, the README rewrite was about `/bob-compliance`. Model is the new addition; if the user wants a README update later, that's a separate follow-up — out of scope here).

Correspondingly, the spec's §7 test #5 (`claude_md_workflow_lists_bob_model`) is **dropped** from this plan. The 4 remaining tests are sufficient.

### 2. Skill is content-heavy markdown — TDD via token-presence

The bob-model.md template is ~450 lines of structured prose (frontmatter + 5 stages + 三段式 examples + schemas + Mermaid examples). This plan follows the same pattern as bob-compliance:

- The test `init_creates_bob_model_skill` is a single token-presence loop that accumulates assertions across Tasks 2, 3, 4.
- Each task writes the prose for one or two stages AND extends the test to assert that stage's load-bearing tokens.

This is consistent with `init_creates_bob_compliance_skill` / `init_creates_bob_nfr_skill` / etc. Style reference for prose tone: `src/templates/skills/bob-compliance.md` (most recent, closest sibling).

### 3. md SSoT, HTML view — Claude generates both at runtime

The spec is clear that `/bob-model` always emits **both** `docs/bob/03-model-<slug>-<date>.md` (SSoT) **and** `docs/bob/03-model-<slug>-<date>.html` (view). Both are runtime outputs of the skill — NOT init/upgrade assets. This plan does not test the .md or .html content; we test that the **skill template** instructs Claude to produce both, via tokens like `.md`, `.html`, `Mermaid`, `CDN`, `classDiagram`, `stateDiagram-v2`.

### 4. HTML strategy: CDN + graceful degradation

Per the spec, the HTML is single-file, self-contained, with Mermaid loaded via CDN:
- `<script src="https://cdn.jsdelivr.net/npm/mermaid@10/dist/mermaid.min.js"></script>`
- Offline degradation: Mermaid script not loaded → `<pre><code class="language-mermaid">…</code></pre>` blocks remain visible as raw DSL text
- HTML is committed to git (NOT in `.gitignore`); team uses PR for review

The skill's Stage 3 prose must explain this strategy so future readers and Claude understand the trade-off.

### 5. Asset flag profile is identical to every other bob-* skill

For the new `Asset` entry in `src/assets.rs::HARNESS_ASSETS`:
- `category: Category::Skill`
- `included_in_minimal: true` — minimal installs all skills, same as the other 7
- `upgrade_safe: true` — upgrade can refresh the template freely; user doesn't hand-edit skill files

The existing drift-guard test `upgrade_safe_field_matches_category_policy` covers this automatically (all `Category::Skill` entries must have `upgrade_safe=true`). No drift-guard modification needed — unlike the compliance feature where we extended the HarnessDoc allowlist.

### 6. Append to bob-survey "下一步", don't restructure

`bob-survey.md`'s `## 5. 下一步` (around line 293) already lists 3 recommended commands by difficulty (Easy / Medium-Hard / 🔴). Task 5 appends ONE new line at the end of that list — the model recommendation. **Don't** reorder or rewrite the existing 3 lines.

````markdown
## 提问规约(强制三段式)

任何需要用户选择的问题,**必须**按下面三段式输出。**禁止**抛开放问题。

格式:

> **[问题序号] [问题]**
>
> **推测**:<你的判断>
> **理由**:<一句话>
> **推荐选择**:`<具体一个选项>`
>
> 是否同意?(回"是"走推荐;回"否,理由是 ..."重判;回"否,我选 X"切到 X)

## 目标

**翻译**散文需求文档为下游可消费的领域模型快照。只回答两个问题:

1. **这份需求里的术语 / Entity / 业务规则 / UseCase 各是什么?**
2. **PM 没说清楚、需要交给 `/bob-spec` 进一步消化的开放问题有哪些?**

**不写代码、不切 story、不画架构**。产出一份 md(SSoT)+ 一份 html(团队视图)。

## 工作流(5 个 Stage)

```
Stage 0. 入口体检 + 短路判定(可跳过建模)
Stage 1. 抽取(术语 / Entity / 规则 / UseCase / 开放问题)— 三段式追问填空
Stage 2. 写 md(SSoT,下游消费)
Stage 3. 写 html(视图,团队 PR review)
Stage 4. 三段式收口 + 通报下一步(/bob-stories 或 /bob-identify)

> **Q0: 这份需求需要单独建模吗?**

> **理由**:`<具体证据:行数 / 概念数 / 跨 story 共享规则数>`

输出文件名计算:
- `<slug>` = 源文档名去后缀(`ycb需求.md` → `ycb`,`阿里规约.pdf` → `阿里规约`)

`--refresh` flag 显式触发 Stage 1,即使 Stage 0 判定为"极小需求"。
````
